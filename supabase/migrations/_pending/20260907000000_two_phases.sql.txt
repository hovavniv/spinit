-- Renames the event_phase enum labels to match what they now mean in the app.
-- The app was collapsed from four phases to two on 2026-09-06; the two stored
-- values 'dinner' and 'open-floor' became the reception and party phases, but
-- kept their old labels because renaming needs the two-step below and there was
-- an event live at the time.
--
-- WHY TWO STEPS: Postgres will not let a value added by ALTER TYPE ... ADD VALUE
-- be used in the same transaction that adds it. Supabase runs each migration in
-- a transaction, so the ADD and the UPDATE cannot share one file. Run part 1,
-- let it commit, then run part 2.
--
-- Live data at the time of writing (2026-09-06): 256 rows on 'dinner', 1 on
-- 'open-floor', 6 null, and ZERO on 'cocktails' or 'last-dance'. Re-check that
-- before running -- the UPDATE below assumes nothing needs rescuing from the
-- two labels that are being retired.

-- ---------- part 1: add the new labels (own migration, own transaction) ------
alter type public.event_phase add value if not exists 'reception';
alter type public.event_phase add value if not exists 'party';
